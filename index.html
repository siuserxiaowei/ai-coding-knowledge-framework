01 / FOUNDATION

复杂度是软件工程的第一公敌

软件工程所有讨论最终都汇到一点：人脑能装的东西有限。管理复杂度不是技巧问题，是哲学问题。

cognitive load change amplification unknown unknowns tactical vs strategic deep modules

Ousterhout 把复杂度拆成三个可观察的症状。前两个能算，第三个连边界在哪都不知道——那才是真正致命的。

OUSTERHOUT — THREE SYMPTOMS OF COMPLEXITY

战术编程 vs 战略编程

工程师可以分成两类。Ousterhout 的论点是这两条路线复利方向相反，三年后两个人写出的代码库会完全不同。

TACTICAL

每次都求当下最快通过。绕开难题、糊上 patch、"以后再说"。短期速度高，但每次都让总复杂度增加。债复利成负。

STRATEGIC

愿意先多花 10–20% 时间换更好的结构。看起来慢，但每次都让总复杂度下降。能力复利成正。

深模块 vs 浅模块

好抽象的界面应该简单，实现应该复杂——因为调用方只需要看界面。浅模块（界面跟实现差不多复杂）什么都没掩盖，只是加了一道砖墙。"信息隐藏"不是 OOP 教条，是调用方不应该需要知道你怎么实现。

三条实战原则

  • Define errors out of existence——把错误重新定义成正常情况，不需要 handle。最少代码 = 最少错误。
  • Design twice——任何重要 design 都至少做两版完全不同的方案做对比，再选。
  • 注释是 design 的一部分——如果一个东西难注释，通常意味着 design 没想清楚。
复杂度是增量的——它不是某次糟糕决定造成的，是无数次"小妥协"复利出来的。
所以战略编程不是某次大重构，是一种持续的纪律。 JOHN OUSTERHOUT — A PHILOSOPHY OF SOFTWARE DESIGN
02 / SPEC ENGINEERING

Spec 是强制 design 的工具

写 spec 不是为了文档好看，是为了在还能扔掉的阶段把 design 做完。

spec forces design declarative vs imperative spec/status separation 12-factor PEP process

Joel Spolsky 的论点

Joel 1999/2000 写 Painless Functional Specifications，核心论点不是"文档很重要"，而是写 spec 强制你在还能扔掉的阶段做 design。"程序员对自己的代码会产生感情，写出来后想扔掉重写非常难。" Spec 阶段成本是分钟级，code 阶段是周级。

JOEL SPOLSKY — COST OF REWRITING BY STAGE

Spec 还顺带消除三种隐性成本：让沟通只发生一次（不必一遍遍口头解释）、让排期变可能（没 spec 谈不上估时）、把延后的决策强制提前（避免决策堆积到最后崩盘）。

K8s API conventions：工业级 spec 范本

Kubernetes 给"spec 应该长什么样"提供了最完整的公开范本：

A

声明式而非命令式

用户写"desired state"，控制器去 reconcile。系统朝最新意图收敛，不依赖经过中间状态。

B

spec / status 严格分离

spec 是用户意图（用户写、控制器读），status 是系统实况（控制器写）。两者权限可以不同。

C

optional / required 显式

每个字段要么显式 optional，要么显式 required。不允许中间态、不允许"看情况"。

D

conditions 而非 phase enum

状态用条件数组（type/status/reason/message/time），可以叠加新条件不破坏旧读者。

E

opaque resourceVersion

乐观并发，靠 ETag-like 重试。客户端必须把它当不透明字符串，不准 parse。

F

lists over maps

API 对象不该用"键是数据"的 map，应该用带 name 字段的 list。所有 JSON 键都是字段，不是数据。

12-Factor App：deploy 维度的 spec

12 条规则的核心是 declarative automation + 干净的 OS 契约 + 最小化 dev/prod 偏离。最被忽略的几条：backing services 是 attached resources（数据库、缓存、队列对应用是可替换资源）；logs as event streams（应用只往 stdout 流出，由 deploy 环境决定收集去哪）；scale via process model（横向扩展，无状态进程）。

因子规则本质
III. Configconfig 走 env，不入 code不允许配置写死
IV. Backing Services视为 attached resourcedb/cache 可替换
V. Build/Release/Run严格三阶段分离release 不可在运行时改
VI. Processes无状态进程state 进入 backing service
IX. Disposabilityfast startup, graceful shutdown进程随时可杀
XI. Logslogs as event streams应用不知道日志去哪

TigerStyle 把 spec 推到极端

TigerBeetle 的风格指南本身就是工程文化的硬契约：70 行函数硬上限、100 列硬上限、零依赖、命名按显著性递减（latency_ms_max 而非 max_latency_ms——让相关变量排序后视觉对齐）。一份风格指南做到这种密度，本质上就是把"我们怎么写代码"这件事可执行化。

Art is born of constraints.
The rules act like the seat-belt in your car: initially they are perhaps a little uncomfortable, but after a while their use becomes second-nature and not using them becomes unimaginable. TIGERBEETLE — TIGER_STYLE.md
03 / CODE DISCIPLINE

代码纪律——让"读"赢，不让"写"赢

代码被读的次数远多于被写。所有"花更多时间写"的纪律本质都是为了让所有未来的读者省时间。

assertions positive + negative space naming as ontology no recursion push ifs up, fors down

Assertion 是 multiplicative intelligence

TigerStyle 的核心论点：assertion 不是 debugging 工具，是把 mental model 写下来的契约。每条 assert 是一次"我相信此处状态是什么"的声明。规则有四条：

RULE 01

密度 ≥ 2 / 函数

每个函数至少两条断言。没断言的函数意味着没人在记录 mental model。

RULE 02

Pair across paths

同一性质在两条独立路径上分别断言（写盘前断一次、读出后再断一次）。

RULE 03

正负空间都断言

既断言"这是真"也断言"这不可能"。正空间漏了的反空间会兜住。

RULE 04

Compound 拆分

assert(a); assert(b); 优于 assert(a and b);。失败时知道哪个崩了。

命名学：每个字符都是有理由的

TigerStyle 把命名提升到本体论的高度。每个选择都有可证明的理由：

规则原因
snake_case下划线代表空格，最接近自然语言阅读节奏
不缩写缩写 grep 不到。req 既可能是 request 也可能是 require
显著性递减latency_ms_max 而非 max_latency_ms，让相关变量排序后视觉对齐
callback 在参数末尾它实际被调用的位置也是最后，参数顺序 = 调用顺序
用名词不用现在分词replica.pipeline 而非 replica.preparing——名词在文档里组合性强
带语义前缀gpa: Allocator（general purpose）vs arena: Allocator——名字告诉你要不要 deinit

控制流：可预测性优先于聪明

  • No recursion——栈深度无界等于把可观察性交给运行时。能用循环就不用递归。
  • 所有循环必须可证明有界——上限要么是编译期常量、要么有显式 break 条件。
  • 复合条件拆成嵌套 if/else——让 positive space 和 negative space 都被显式处理，不留默认 fallthrough。
  • 所有错误必须 handle——92% 的灾难性故障源于错误处理不当（Yuan et al. OSDI 2014）。
Push ifs up and fors down. MATKLAD — 控制流优化口诀

把判断推到调用点（上层有机会让整条分支被消除），把循环推到最底层（可以批处理、amortize 开销）——一条口诀浓缩了一整套思想。

内存与生命周期

  • 静态内存分配——所有内存在启动时分配，运行时不再分配。OOM 不再是运行时问题。
  • 不复制变量、不取别名——减少同步漂移的可能。
  • 大 struct 原地构造——通过 out-pointer 初始化，消除中间拷贝。In-place 一旦开始就是病毒式的。
  • 资源分配/释放视觉对齐——用空行分组，让泄漏在 diff 里一眼可见。

Anomaly 三件套：人为制造灾难

SQLite 通过 instrumented 替换系统性模拟最不利路径：

  • OOM 测试——通过 malloc shim 注入"第 N 次分配失败"，循环 N 直到不再失败。每条路径上 OOM 都不能破坏 invariant。
  • I/O 错误测试——通过 VFS shim 模拟磁盘错误。读/写/同步任一失败都要恢复。
  • 断电测试——VFS 在指定 I/O 后快照，重启时重放并注入真实断电损坏模式（reorder/truncate/garble unsynced writes）。

Mutation testing：把测试本身测一次

把源码里每个 branch instruction 变成无条件跳转或 nop，看 test suite 能不能抓住。能抓住才证明这个 branch 真的有意义——也证明你的 test 真的在 test。

Antithesis：决定性模拟测试

Antithesis 把方向推得更极端。他们的核心论点扎实到令人窒息：

If you had the foresight to write a test for a particular case,
then you probably had the foresight to make the code handle that case too. WILL WILSON — ANTITHESIS

传统测试只能 cover 你预见到的失败模式——而 bug 本质上是预见不到的。Antithesis 的方案：整个系统跑在 hypervisor 上，事件顺序、网络延迟、机器崩溃都可重放。bug 一旦出现，无论你的软件当时在干什么疯狂的事都能完美重现。FoundationDB 用这套方法让小团队跑出 50x productivity。

Stripe Scientist：online migration 的灵魂

Scientist library 是同方向的轻量版：dual-read 时同时跑新旧实现并对比差异，任何不一致自动告警。没有 Scientist 你只能靠祈祷——所以它是 Stripe 4-phase 在线迁移能跑通的根本依赖。

05 / API CONTRACT

接口与契约的工业实践

分布式系统的两难——一切都可能丢失、重复、乱序。好契约用结构而非希望对抗这一切。

declarative state optimistic concurrency idempotency exponential backoff status conditions

K8s 的契约设计精华

除了 spec/status 分离（已在 §2 讲过），K8s 还有几条值得抽出来：

机制解决的问题
resourceVersion 乐观并发不加锁，靠重试。客户端 GET → 改 → PUT，若并发冲突返回 409，客户端 retry
status conditions 数组不用单一 phase enum，用 type/status/reason/message/time 条目数组——可叠加新条件而不破坏现有读者
无浮点入 spec浮点 round-trip 精度损失。要数字就用 int32/int64，不准用裸 int
字符串枚举优于 boolbool 字段未来扩展时只能加新字段；枚举可加新值
lists over mapsAPI 对象用带 name 的 list 而非 map。所有 JSON 键是字段（schema），不是数据
same-namespace refs跨 namespace 引用引入权限边界 + 引用完整性问题。能不跨就不跨

Stripe Idempotency：异步系统的基石

网络是不可靠的——网络可能在三个阶段失败：请求未到、处理中、响应未回。任意阶段失败客户端都无法分辨"事情做了没"。幂等性就是把"做了/没做"这件事的不确定性消除掉。

天生幂等

HTTP PUT 和 DELETE——重试任意次结果一致。设计 API 时应该多用这两个动词。

需要 Idempotency-Key

POST 等副作用操作——客户端必须传唯一 key，服务端缓存结果，按 key 返回。否则重试会重复扣款。

配套必须的：指数退避 + jitter——避免所有客户端同步重试形成 thundering herd，把恢复中的服务再砸一次。

Handle failures consistently. Handle failures safely. Handle failures responsibly. STRIPE — IDEMPOTENT API DESIGN
06 / SCHEMA EVOLUTION

Schema 演进——时间维度的契约

改一张活的表跟改一段死的代码完全不同——你在和"昨天的自己"、"昨天的写者"、"昨天的读者"同时谈判。

dual-write backfill observation window level-based reconciliation rollback path

Stripe 4-phase 在线迁移

STRIPE — FOUR-PHASE ONLINE MIGRATION

K8s level-based reconciliation

同一脑回路用在分布式状态同步上：状态从 A → B → C 时，B 可能根本没被任何观察者看到，因为 controller 是 level-based（看最新状态收敛）不是 edge-based（响应事件）。这意味着所有变更必须用"我把状态 declared 为 X"而不是"我触发了从 X 到 Y 的转换"——否则 missed edge 就是丢数据。

07 / AGENT DESIGN

AI Agent 设计——控制流的新维度

workflow 的控制流由代码定，agent 的控制流由 LLM 定。中间是一个按复杂度递增的梯度，每一档都该有理由跳上去。

workflow vs agent augmented LLM orchestrator-workers evaluator-optimizer ACI

Anthropic 的复杂度梯度

从最简单的"augmented LLM"到完整自主 agent，每跳一档都要测量证明真的有改善。

ANTHROPIC — WORKFLOW PATTERNS TO AUTONOMOUS AGENTS

Agent-Computer Interface (ACI)

Anthropic 最被低估的论点：你给 agent 的 tool 就像给人的 UI。设计要按 poka-yoke（防呆）原则：

  • 参数命名要清晰，描述要具体，给例子和边界条件
  • 避免要数行号的 diff 格式——模型不擅长数
  • 避免 JSON 转义嵌套——每层转义都增加错配概率
  • tool 间不能模糊重叠——"人无法分辨该用哪个 tool 时，agent 也分不出"
  • tool 集合要小而精，不要堆一大堆

Karpathy 的 Software 2.0 视角

传统 Software 1.0 是程序员"在程序空间里选一个点"；Software 2.0 是"指定目标，让优化在程序空间里搜出一个点"——数据集就是 source code，神经网络权重就是 binary。Agent 不完全是 2.0，但用了它的核心思维：你不再写程序，你写约束和目标，让模型在执行时合成路径。

Neural networks are not just another classifier, they represent the beginning of a fundamental shift in how we develop software. They are Software 2.0. ANDREJ KARPATHY — SOFTWARE 2.0
08 / AI CODING PRACTICE

AI 编程实战——把 LLM 当成什么

不是把代码外包给 LLM，是和 LLM 协作压缩你的意图。人写约束和签名，模型填实现，人保留"它是否真的能跑"的最终判断权。

context engineering just-in-time retrieval right altitude repo map authoritarian mode

Context Engineering 的核心一句

Find the smallest possible set of high-signal tokens
that maximize the likelihood of your desired outcome. ANTHROPIC — EFFECTIVE CONTEXT ENGINEERING FOR AI AGENTS

上下文是有限资源——存在 "context rot" 现象（transformer 的 n² attention 让 token 越多反而稀释信号）。所以工程问题是压缩 + 即时调取，不是塞更多进去。

CONTEXT ENGINEERING — COMPRESS, DON'T DUMP

四件套技术

01

Just-in-time retrieval

保留路径/查询/标识符，用工具按需拉数据。Claude Code 就是范本——不预加载 codebase，靠 grep/glob 即时拉。

02

Compaction

对话过长时摘要历史。"先优化 recall（不丢关键信息）再优化 precision（不带冗余）。"

03

Structured note-taking

让 agent 在 context 外维护持久笔记，需要时拉回来——agentic memory。

04

Sub-agents

拆任务到子 agent 各自小窗口，只把 1000-2000 token 的汇总返回给主 agent。

"Right altitude" — System Prompt 的最佳高度

太具体

每个 case 都 hardcode 规则，prompt 变得脆且难维护。模型刚学会就被新规则盖过。

RIGHT ALTITUDE

足够具体能指导行为，足够灵活让模型自己找路径。可观测到失败时再加例子，不预先填满。

Simon Willison 的六条实战提炼

  • LLM 是"花哨自动补全 + 对话内记忆"——是"过度自信的、闪电快的结对伙伴"，不要神化也不要鄙视。
  • 训练截止意识——对截止后发布的库会胡说。对策是用稳定老牌库 + 主流写法。
  • 上下文是一切——同一对话内连续追问比新对话从头开始有效得多。
  • Production code 进入"权威主义模式"——给函数签名让它填实现，比让它自由发挥效果好得多。
  • 不能把"测它真的能跑"外包给机器——LLM 可以写测试，但你必须看它跑。
  • LLM 放大现有专业能力——你 prompt 的质量 = 你领域知识的深度。专家用 LLM 跑出 10x，新手反而被拖到 negative。

Aider 的 repo map：结构性压缩 > 截断

Aider 给了 AI 编程上下文工程一个具体范式：tree-sitter 提取每个文件关键符号 + 签名 → PageRank 式按相关度排序 → 按 token 预算压缩——而不是塞整个文件。原则是 AI 需要的是"代码的架构"不是"代码的实现"。

Aider 还教了另一件事：edit format（whole file / diff / search-replace block）是工程决策不是默认——每种格式对应不同的模型能力曲线，必须实测，不能假定。

09 / META-PRINCIPLES

横切的元原则

读完九个方向后浮现的几条规律——它们在不同领域以不同方式出现，但形状相同。

META 01

简单是反复练出来的

"Simplicity is unpopular because it requires hard work and discipline"（Dijkstra）。TigerStyle 的硬限制、Anthropic 的 start simple——所有人都同意简单不是自然涌现的，是反复约束自己换来的。

META 02

约束是创造的助产士

"Art is born of constraints"（TigerStyle）。12-factor 的 12 条限制反而让云时代 deploy 工业化；K8s "无浮点入 spec"看着古怪，全是 hard-won 经验。

META 03

显式打败隐式

K8s 的 optional/required 必须显式、Stripe Idempotency-Key 必须传入、TigerStyle "正负空间都断言"——所有这些都在禁止"假设""默认""你以为"。代码里没说的事，迟早会以最贵的方式被发现。

META 04

二维思考、双路径验证

TigerStyle pair assertions、Stripe Scientist dual-read、SQLite optimization-on-vs-off 等价测试、mutation testing——好工程不是单点验证，是同一性质在两条路径上同时检查，让 invariant 自然涌现。

META 05

审计 / 可观测性必须内建

K8s status conditions、Stripe Scientist、SQLite 200 项 release checklist、TigerStyle "comments 必须解释 why"——可追溯不是事后想起来加的，是设计阶段就嵌进去的。

META 06

读代码比写代码难

Aider repo map、Ousterhout 信息隐藏、TigerStyle 命名学、K8s lists-over-maps——所有"花更多时间写"的纪律，本质都是为了让所有未来的读者（包括 AI、包括未来的自己）省时间。

META 07

测试是把未知映射到已知

SQLite 和 Antithesis 的本质相同——你不能写出"涵盖未知未知的 test"，但你可以建系统化探针去 enumerate 那些你没想到的输入空间。

META 08

AI 编程是协作压缩意图

从 Karpathy 的"指定目标搜空间"，到 Anthropic 的"高信号 token 最小集"，到 Aider 的"repo map 不是全文件"——人写约束和签名，模型填实现，人保留最终判断权。

以上这一切都在做同一件事——
把"靠记性 / 靠纪律 / 靠默契"换成"靠系统、靠工具、靠契约"。

大神和普通工程师的差距，不在于谁更聪明，
在于谁更不依赖聪明。 通读完所有资料后的最终一条

压缩成一句

好工程是结构化的纪律，对抗的是熵——而 AI 时代的"纪律"多了一个新维度：对模型可见的纪律（spec、tool 设计、context 工程）。所以 spec stack 不再是软文档，是 agent 的 runtime 之一。
